## Статус · ДЗ відправлено

- Лабораторну L10 завершено на `qwen2.5:7b`. [Результати пілота](lab-recommendation-draft.md)
- Повне калібрування завершено. Локальний суддя збігся з розміткою на 17/30 кейсах, хмарний — на 25/30. [Локальний звіт](../evals/reports/calibration-l09_labels-schema-20261107T160535826977Z.json)
- Рішення — залишити хмарного суддю в релізному гейті з ручною перевіркою. [Фінальна рекомендація](../model-selection-recommendation.md)
- Матеріали опубліковано в `main`. Посилання на репозиторій подано на платформі. Очікуємо перевірку.

## Початковий план

Стан підготовки на 7 листопада 2026 року. Мета — вирішити, чи переносити суддю ескалації PayPilot усередину периметра, на яких умовах і скільки часу це додасть до релізного прогону. Етапи роботи успадковують підхід ДЗ8: зафіксовані дані й прогноз, офлайн-перевірки, малий пілот, повний прогін, звірка сирих доказів і відтворення з чистого клону.

## Що дають лекція, лабораторна й ДЗ

- **Лекція.** Перенесення судді змінює маршрут запиту з питанням, записаною відповіддю й рубрикою. Перевірити маршрут судді, окремо описати агента, трасування, сховища та доступ до них. JSON-схема забезпечує форму відповіді. Дослівність цитати й правильність вердикту перевіряються окремо. Контракт фіксує підтримку `format`, розмір файлу моделі, температуру, тег і дату. До відтворюваної конфігурації додаємо повний digest, версію runtime і режим виклику.
- **Лабораторна.** Перед запуском записати прогноз. Далі самотест із контейнера, один спірний кейс по 3 рази зі `schema` і `none`, потім 12 кейсів × 5. Окремо зберегти валідність JSON, стабільність вердиктів і підтвердження цитат. На тих самих 12 кейсах зіставити локальний результат із хмарним, виміряти час і зробити чернетку рекомендації.
- **ДЗ.** Повторити калібрування на всіх 30 незмінних кейсах ДЗ8, з `rubric.v1` і `runs: 5`. Подати обидві заяви довіри, обидва звіти, конфігурацію без ключів, рекомендацію із семи розділів, універсальний шаблон і команду для L13.

## Протокол порівняння

Хмарна база — чинний офлайн-перерахунок ДЗ8 для `claude-haiku-4-5-20251001`, temperature 0,7, `rubric.v1`. Загалом **25/30**, Wilson 95% **66,4–92,7%**. На спірних **5/10**, Wilson **23,7–76,3%**. Самоузгодженість **29/30**. На лабораторному зрізі ДЗ8 (`HW8-01–04`, `HW8-11–14`, `HW8-21–24`) із цих самих хмарних рядків виходить **10/12** узгоджених і **11/12** стабільних, спірні **2/4**. Зберегти вибір зрізу до локального запуску. `HW8-22` — кандидат для однокейсової перевірки схеми.

Для обох сторін оцінювати перші п’ять спроб без заміни невалідних. Помилка формату, протоколу чи недослівна цитата дає `MISS`. Для вердикту кейса потрібні щонайменше три однакові валідні голоси. Для стабільності потрібні п’ять валідних однакових голосів. Wilson рахується по кейсах. Порівняти всі кейси і спірну третину окремо. Якщо інтервали перекриваються, записати «не відрізнити на цьому обсязі». Розкласти пропуски, хибні тривоги й `MISS` по трьох групах і назвати спільний клас промахів.

Для локального судді стартовий режим — один виклик, `schema`, temperature 0 за лабораторною. Температуру, формат і режим мислення записати явно. Порівняння стосується двох зафіксованих конфігурацій, зокрема різних температур, тому результат сам по собі не ізолює ефект моделі.

## Послідовність робіт

1. **Перенести базу в ДЗ9.** Скопіювати незмінні labels і `rubric.v1`, перевірити SHA-256, додати джерело freeze з ДЗ8, хмарну заяву й звіт у `evals/reports/`. Зберегти точні байти в Git і перевірити на чистому клоні. Зафіксувати підмножини 1 і 12 окремими похідними наборами, повний файл залишити джерелом.
2. **Підготувати локальний шлях запуску.** Використати реалізацію з офіційного `paypilot-l10-eval@d746c0f` для Ollama, схеми й таймінгів. Налаштувати `STAND_DIR` на `paypilot-stand-shared`, якщо потрібен імпорт стенду. Для порівняння з ДЗ8 перенести потрібні частини адаптера й звітності, зберігши strict scoring і сирі відповіді. Калібратор лектора використовує найчастіший вердикт і рахує дослівність цитат окремо. Звіт із ним придатний для лабораторної, а порівняння з перерахунком ДЗ8 потребує однакового правила більшості й MISS. Для ДЗ9 джерело даних — наші зафіксовані 30 кейсів. Набір лектора використовувати лише як приклад. Підтримати `JUDGE_FORMAT=schema|json|none`, таймінги, окрему валідацію цитат, звіти з моделлю та `runs`. Для локального запуску перевіряти SHA-256 і обмежити endpoint локальним Ollama. Зберегти блокування хмарних викликів. Офлайн перевірити тіло HTTP-запиту, відсутність fallback, обробку MISS та запис результатів. Для відтворення підготувати Compose і `judge.local.env` без секретів.
3. **Підняти Ollama і зафіксувати прогноз.** На цьому комп’ютері початковий кандидат для перевірки контракту — менший `qwen3.5:4b`; Модель має пройти ліміт лекції **≤6 GB** за фактичним розміром локального артефакту. `qwen3.5:9b` із наведеним у лекції розміром 6,6 GB виходить за цей ліміт. Це вибір кандидата для пілота. У Windows встановити і запустити Ollama, завантажити локальний тег і перевірити `/api/tags` на `localhost:11434` з хоста, а з Docker — на `host.docker.internal:11434`, записати версію Ollama, тег, digest і розмір конкретного локального артефакту. Робоча гіпотеза до самотесту для 4B — **9/12** збігів, перші промахи на спірних формулюваннях непрямого запиту на людину або запевнення результату, **15–45 с/виклик** на CPU як неперевірена оцінка для планування. Записати прогноз до першого inference, потім звірити з виміром.
4. **Пройти лабораторну.** Самотест, `HW8-22` × 3 у кожному з двох режимів, далі зафіксований зріз × 5 зі схемою. Порівняти з відповідними хмарними рядками, порахувати wall-clock / 60, окремо позначити cold load і помилки. Зробити чернетку рекомендації. Перед повним прогоном перевірити, що формат, шлях і журнал спроб відтворюються, та оновити прогноз часу.
5. **Провести повне локальне калібрування.** 30 × 5 = **150** спроб, той самий локальний контракт, без нових звернень до агента. Зберегти сирі спроби й звіт `reports/calibration-l09_labels-*.json` для команди курсу, подати звіт разом із хмарним у `evals/reports/`. Офлайн звірити кількість спроб, вердикти, групи й Wilson. У лабораторній і повному прогоні зберегти wall-clock, кількість запитів, режим і стан прогріву.
6. **Порахувати економіку й оформити рішення.** Для локальних викликів ціна API за токени — 0, окремо врахувати залізо й час. Для хмарного калібрування використати зафіксовану оцінку ДЗ8 USD 0,182620 за перші 150 спроб. Для релізного набору `l09_escalation` є 5 judge-кейсів. Поточний runner ДЗ8 судить останню з п’яти відповідей, тож фактичний режим дає 5 викликів судді за реліз. Формула шаблону з оцінкою кожного повтору дає 25. Показати обидва режими окремо, вказати чинний і виміряти або оцінити секунди як кількість викликів × `t_local`. У рекомендації обґрунтувати вердикт, умови й контрфактичний мандат Zero regulatory risk. Зберегти ручну перевірку ескалації на релізі з ДЗ8 як вихідну умову.
7. **Перевірити здачу.** Поруч мають бути `judge-trust-statement.md` і `judge-trust-statement.local.md`, `model-selection-recommendation.md` із сімома розділами, узагальнений `model-selection-recommendation.template.md`, `judge.local.env`, звіти в `evals/reports/` і README з фактичним тегом та датою. На чистому клоні перевірити команду L13 `JUDGE_MODEL=ollama:<тег> docker compose run --rm --entrypoint python eval tools/calibrate_run.py l09_labels`. Для PowerShell задати змінну й передати її контейнеру через Compose. У звіті має бути `judge_model`, у публічному дереві — лише матеріали, придатні до публікації, без `.env` і ключів.

Документація runtime: [Ollama для Windows](https://docs.ollama.com/windows), [structured outputs](https://docs.ollama.com/capabilities/structured-outputs), [метадані локальних моделей](https://docs.ollama.com/api/tags), [кандидат 4B](https://ollama.com/library/qwen3.5:4b).
